# tors v0.1.0 — design (approved 2026-09-05)

**tors** is a GIL-free text normalization library for CPython, backed by Rust. It exists
because a class of CPython work — single GIL-held C calls over unbounded strings
(`re.sub`, `unicodedata.normalize`, `str.replace`) — stalls the event loop wherever it
runs, and `asyncio.to_thread` cannot bound it. The originating ingestion service
(unreleased) carried a hand-rolled seam-safe chunking workaround for exactly this class;
tors replaces that tier natively: the whole transform in one `py.detach` pass.

## Decisions (locked with the owner)

## API contract (frozen for v0.1)

```python
tors.normalize(text: str) -> str
tors.finalize(text: str) -> tuple[str, str]  # (normalized, sha256-hex-of-utf8)
```

- Pipeline (both): NFC → fold CRLF/CR → drop `[ \t]+` runs before a newline → collapse
  `\n{3,}` to `\n\n` → `str.strip()` (Python's exact whitespace set, incl. 0x1c–0x1f).
  `finalize` additionally returns lowercase-hex SHA-256 of the result's UTF-8 bytes —
  byte-identical to `hashlib.sha256(normalized.encode("utf-8")).hexdigest()`.
- GIL: released for the whole native pass (`py.detach`). The GIL-held residue is pyo3's
  argument extraction plus return marshalling: for ASCII or already-cached strings the
  borrow is a zero-copy alias and the residue is the O(output) marshalling; on the first
  call for a non-ASCII input, `&str` extraction (`PyUnicode_AsUTF8AndSize`) builds and
  caches a UTF-8 copy of the input under the GIL — O(input), ~20ms at 12MiB measured.
  Callers that care keep a `to_thread` wrap — the originating service's swap-in (M3)
  keeps one for exactly this reason.
- Argument extraction is a zero-copy borrow for ASCII/cached inputs (no allocation
  beyond the output); a one-time O(input) UTF-8 materialization otherwise.
- Unicode tables: tors's own (`unicode-normalization` crate). **Headline guarantee: same
  input → same output/hash on every supported interpreter (3.10–3.14)** — a property
  CPython's per-version `unicodedata` cannot promise; this is what makes tors safe for
  hash-gated dedupe. Per-version parity with each interpreter's own `unicodedata` is
  pinned by the oracle tests running on every matrix leg.

## Correctness proofs (test suite)

1. Existing suites stay: behavioral cases, exhaustive ≤4 over the trigger alphabet,
   hypothesis ×2 (vs a pure-Python reference oracle using the *running* interpreter's
   `unicodedata`), seeded-random.
2. NEW exhaustive NFC sweep: every canonically-decomposable codepoint —
   `tors.normalize(NFD(c)) == unicodedata.normalize("NFC", NFD(c))` — plus Hangul
   syllable samples. Runs per matrix leg → pins parity with every Python's tables.
3. NEW strip-set parity: for every `chr(c)` where `chr(c).isspace()`,
   `normalize(ws + "x") == normalize("x" + ws) == "x"`; negative pins for non-whitespace
   look-alikes (e.g. U+200B) proving they are preserved.
4. NEW not-NFKC pin: compat ligatures (U+FB01) must NOT compose.
5. NEW finalize consistency property (hypothesis):
   `finalize(t) == (normalize(t), sha256(normalize(t).encode()).hexdigest())`.

## Performance proofs ("provably performant")

1. **GIL proof as a CI test** (the claim, tested, not asserted): worst-heartbeat-gap
   method (10ms ping; ratio-based multi-sample assertion, load-robust on 2-vCPU
   runners). `finalize` at 12MB and ≥32MB corpora: worst gap must sit in the
   marshalling    band (measure first, then budget with ≥5× margin below the CPython
   pipeline's 100ms–1s). A two-size pair (12MB + ≥32MB) proves the residual stays small
   and O(output)-coupled as the corpus grows.
2. Wall-time: tors beats the pure-Python reference pipeline at 1MB/12MB (prose,
   decomposed, CRLF corpora) — asserted in CI with a tolerant margin (same-runner
   comparison) plus full numbers recorded in the README from a quiet local run with
   methodology; 1KiB is measured and recorded but deliberately unasserted (µs-scale
   overhead dominates there).
3. Criterion benches (Rust side): `normalize`/`finalize` at 1KB/1MB/12MB/100MB with an
   in-repo corpus generator; `cargo bench` locally, `--no-run` in CI; guards against
   tors's own regressions across versions.

## v0.2 surface (added 2026-09-06; owner-approved from the audit's measured ranking)

- `tors.decode_utf8(raw: bytes, *, errors: "strict" | "replace" = "strict") -> str`
- `tors.finalize_utf8(raw: bytes, *, errors: "strict" | "replace" = "strict") -> tuple[str, str]`
  — decode + normalize + hash in one native call; the shape an extraction pipeline
  wants for its text reads (tolerant reads use `errors="replace"`, hence BOTH modes with `strict` as the default —
  a documented deviation from this section's original literal default-only annotation,
  ruled sound in the v0.2 spec review because strict-only cannot serve the stated consumer).
- `tors.b64_encode_bytes(raw: bytes) -> str` — RFC 4648 standard alphabet, padded;
  parity with `base64.b64encode(raw).decode("ascii")` (an OCR content-addressing path,
  ~150ms GIL-held at a 100MB document cap today).
- GIL: `PyBytes` argument extraction is zero-copy — no argument-materialization class
  at all; the only GIL-held residue is the return marshalling (O(output)). The crate
  GIL-model note extends to say so.
- Parity contracts: `decode_utf8` == `raw.decode("utf-8", errors=…)` BYTE-EXACT over
  arbitrary bytes (hypothesis binary strategy; strict raises `UnicodeDecodeError`). If
  Rust's `from_utf8_lossy` diverges from CPython's `replace` on any maximal-subpart
  edge, implement CPython's exact algorithm rather than weaken the pin.
  `b64_encode_bytes` == the stdlib expression over arbitrary bytes (incl. every byte
  value, empty, padding shapes). `finalize_utf8(raw) == finalize(decode_utf8(raw))`.
- b64 DECODE deliberately NOT added (measured 3-4ms at the real MCP cap — a non-issue;
  uniformity is not a reason to grow surface). Chunking and orjson stay out for the
  reasons in D4/§out-of-scope.
- Benches: new cells on the existing ladder; the corpus drift guard extends if any new
  corpus builder appears.

## v0.3 surface (added 2026-09-06; the string core, all parity-pinned)

- `tors.b64_decode(s: str, *, validate: bool = True) -> bytes` — symmetry with
  `b64_encode_bytes`; parity with `base64.b64decode(s, validate=…)` incl. the error
  path (`binascii.Error` subclasses `ValueError` — construct the real class if pyo3
  can, else raise `ValueError` and document the class-name delta).
- `tors.nfc / nfd / nfkc / nfkd(text: str) -> str` — standalone Unicode normalization
  forms (`unicodedata.normalize` is the original GIL-held class); per-matrix-leg parity
  against the running interpreter, same discipline as the v0.1 NFC sweep, extended to
  all four forms.
- `tors.html_unescape(text: str) -> str` — parity with `html.unescape` over the FULL
  HTML5 named-entity table (`html.entities.html5`, with and without semicolons);
  Python's is regex-over-the-whole-string and GIL-held. BUILD GATE: audit the
  originating services for real `html.unescape` call sites first and record the measured
  need; if no site exists, ship anyway as core-library surface but say so in the README
  (honest value statement, not a manufactured claim).
- `tors.grapheme_count(text: str) -> int` and `tors.word_bounds(text: str) ->
  list[tuple[int, int]]` — grapheme/word segmentation via `unicode-segmentation`;
  stdlib has NO equivalent (the gap is the point). API returns OFFSETS not string
  lists (marshalling thousands of small PyStrings under the GIL would eat the win).
  No stdlib oracle exists: tests pin the crate's documented behavior via
  known-tricky cases (ZWJ emoji, combining marks, CRLF-as-one-grapheme, regional
  indicators) + structural properties (monotonic, covering, valid slices).
- Identity statement (README): tors is GIL-free, high-performance text and document
  operations where CPython's stdlib holds the GIL, lacks the capability, or isn't
  fast enough — backed by maintained Rust crates, with parity contracts wherever a
  stdlib equivalent exists.
## v0.4 surface (added 2026-09-06: performance hardening + licensing gate — LANDED 2026-09-06, numbers in README §v0.4)

1. **Quick-check fast paths** — DONE. Every normalization entry consults the crate's
   quick check (`is_nfc_quick(s.chars())` etc.); a Yes skips the pass (the subsumption
   claim verified: ASCII quick-checks Yes under all four forms, pinned by test, and
   the crate's own loop has an ASCII lane — measured 2.4ms against the 94ms NFC
   collect it skips at 12 MiB). `normalize`'s pipeline semantics preserved exactly: a
   Yes skips only the NFC step; the fold/drop/collapse/strip scan still runs, and
   only the complete identity check (item 2) skips everything.
2. **Identity-return contract** — DONE. Quick-check Yes + no CR + no
   trailing-ws-before-newline + no blank-run + no strip delta ⇒ the ORIGINAL
   PyObject returns (`tors.f(s) is s`), zero allocation/copy/marshalling; wrapper
   restructure takes `Bound<PyString>`, borrows `&str` for the detached work, and
   hands the same handle back (CPython's `unicode_result_unchanged` precedent,
   documented in the crate GIL model as the zero-cost path). Applied to normalize,
   the four forms, html_unescape (its no-`&` path generalized to nothing-decodes),
   finalize/finalize_utf8 (string element identity-returns; finalize's hash
   computed from the borrowed input buffer with no output allocation). A post-pass
   output==input comparison completes the contract to `f(s) is s ⟺ f(s) == s`.
   Measured: normalize 123.0→2.89ms, finalize 126.3→7.72ms, nfc 111.2→2.48ms at
   12 MiB already-normalized prose (loads disclosed in the README).
3. **Integrated hashing** — DONE. finalize/finalize_utf8 feed SHA-256 the confirmed
   output bytes as the scan writes them (64 KiB chunks — one pass, not two); the
   identity path hashes the borrowed input. All hash parity pins stayed green.
   Measured effect at 12 MiB ≈ the SHA compute itself (5.2ms delta over the
   hashless path, matching the 4.9ms cold digest); the removed second walk is
   sub-ms on this box's SHA-NI + large-L3 geometry — the design's value is
   structural and it enables the identity path's zero-allocation hash.
4. **memchr sentinel scans** — DONE, measured honestly, kept only where it moved
   the needle: the no-`&` bail (−79% end-to-end) and the identity probe's scans
   (memchr/memmem) converted; the between-entity `&` hop was converted, measured
   +5.4% WORSE on the dense entities corpus (~14-byte gaps — per-call SIMD setup
   loses to a byte loop), and reverted. Segmentation audited: no conversion pays
   (per-segment codepoint counts at parity).
5. **Streaming segmentation** — DONE as `tors.word_bounds_iter(text)`: bounds
   computed under ONE detach at construction (UAX #29 word boundaries are not
   safely resumable mid-text — word-class runs span arbitrary distances — so
   per-batch re-segmentation would mis-boundary), drained one tuple per
   `__next__`. Sequence-parity with `word_bounds` pinned over the full UAX #29
   tricky table + hypothesis. Measured at 12 MiB: worst GIL gap 15.4ms (inside
   the suite's shared budgets, vs the list shape's 428-567ms) and the full drain
   347ms vs the list API's 724ms — faster on BOTH axes. The list API stays for
   small inputs, its 1.0s band still pinned; the 12 MiB prose finalize cells'
   ratio budget recalibrated to 0.60 from the new (3x shorter) wall band. A
   `graphemes_iter` was judged NOT warranted: `grapheme_count` returns an int
   (no marshalling class) — YAGNI, judgment recorded.
6. **Licensing gate (repo-wide, permanent)** — DONE. `deny.toml` with the
   permissive-only allowlist (MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib + two
   documented permissive additions the first tree scan surfaced: Apache-2.0 WITH
   LLVM-exception [target-lexicon, pyo3 build-dep] and Unicode-3.0
   [unicode-ident]) + advisories + bans (multiple-versions warn); `make deny`;
   a cargo-deny-action step in ci.yml's lint job; every dependency's license
   recorded in the README's dependency table. Verified passing today:
   `cargo deny check licenses advisories bans` clean, both feature configs.
 7. **Expansion gate (permanent)** — STANDING POLICY, now enforceable: the
    cargo-deny gate (6) is the mechanical half; the PyPI-landscape check,
    crate-health check, and parity contract remain per-module review steps.
    AMENDED 2026-09-06 (owner policy): usefulness-forward — a module lands if it is
    useful to the Python community OR has a real current consumer; a community need
    counts even with no consumer today, provided the capability is not already
    robustly available in Python (healthy maintained binding → skip, unless the
    incumbent holds the GIL and the GIL-free angle is material).

  is material for async users. Semantics: leftmost-longest, non-overlapping,
  documented precisely; str patterns over str text with CHAR offsets (UTF-8 automaton
  + byte→char offset mapping, ASCII fast path). No stdlib oracle: validity
  properties + a brute-force leftmost-longest pure-Python reference over small
  random corpora + golden overlap cases.

## Red-team remediation pass (added 2026-09-06: the security/parity retargets, deadline, and hardening — LANDED)

The red-team review pass (with executed multi-interpreter differentials)
produced findings the owner adjudicated; each landed decision is recorded
here, all measured numbers load-disclosed in the README/test docstrings.

1. **b64_decode retargeted to the post-gh-145264 machine** (HIGH). CPython
   gh-145264 (March 2026, backports 1f9958f9/3.13 and e31c5512/3.14) changed
   `binascii_a2b_base64_impl`: lenient mode no longer stops at the first
   completed pad sequence (data after padding DECODES — `'Zg==Zg=='` →
   `b'f\x06`'` where the pre-fix machine silently dropped the rest, a parser
   differential CPython fixed as a security issue), and strict mode reports
   a pad at quad position 1 as the length error (`'Z=g='` → count 1) rather
   than "Discontinuous padding". DECISION: tors ships the FIXED machine on
   every interpreter — output must not depend on the Python it runs under —
   with `src/b64_impl.rs` a line-for-line port of the 3.13/3.14-branch
   implementation (the branches are identical). The battery literals were
   re-recorded against real post-fix interpreters (3.13.14; cross-verified
   byte-identical on 3.15.0b2). The live differential is gated on the stdlib
   actually having the fix — detected BEHAVIORALLY (a lenient sentinel
   probe), not by version tuple, because the patch levels are exactly where
   version gates lie: measured on this box, 3.14.0 does NOT have the fix
   while 3.13.14 does, so the review's proposed
   `version_info >= (3,13,14) or >= (3,14)` predicate would misfire on
   3.14.0. Pre-fix stdlibs run the comparison recorded-not-asserted (each
   divergence printed); 3.10's entirely different regex validator
   ("Non-base64 digit found", accepts `'Zm9v='`) is a documented divergence,
   never a parity target. The same pass's LOW: a str holding lone surrogates
   now raises the stdlib's plain ValueError (the argument is taken as
   `Bound<PyString>` and the borrow's UnicodeEncodeError is mapped) instead
   of pyo3's own — the stdlib's `_bytes_from_decode_data` converts the same
   encode failure to that ValueError.
2. **diff_opcodes deadline_ms** (MED). `tors.diff_opcodes(a, b, *,
   deadline_ms: float | None = None)`: the bounded Myers search's work on
   hard inputs (few anchorable unique records; a character-level permutation
   is the measured shape — new corpus builder
   `reference.diff_pair_char_shuffled`) grows roughly ~n² with size
   (measured, dev box, load 2.6-3.7: 50k chars 0.32 s, 200k 3.67 s, 400k
   13.81 s, 1M 183.6 s; the README's diff section carries the ladder). The
   kwarg bounds the WHOLE call via similar's deadline mechanism
   (`capture_diff_slices_deadline` — verified in similar 3.2.0's source: it
   has NO error surface for expiry, it only degrades to an approximation,
   so the expiry verdict is tors's own post-call check) and raises
   `TimeoutError` naming the elapsed cost and the deadline; `None` is the
   previous behavior exactly; non-positive/non-finite values are refused
   with `ValueError`. GIL model unchanged: the budget check is plain Rust
   inside the detached pass and the exception is constructed after the GIL
   is reacquired.
3. **html_unescape integer-parse limit** (MED). CPython 3.11+ raises
   ValueError from `int()` for DECIMAL numeric refs whose digit run exceeds
   `sys.get_int_max_str_digits()` (default 4300); tors previously classified
   them to U+FFFD. DECISION: implement the limit in the numeric-ref path —
   read from the running interpreter ONCE per call under the GIL (µs-scale:
   the whole tiny-entity call including the read measures ~0.5 µs; a Python
   call per REF would be a real cost), raised with CPython's exact message

## Red-team remediation pass 2 + the v0.8 community extension (added 2026-09-06 evening — LANDED)

The second red-team review (five-interpreter differential execution: 3.10.21,
3.11.16, 3.12.7, 3.13.14, 3.14.0 against the abi3 wheel, an 8,000-case
randomized b64 differential per interpreter, deterministic diff/parity sweeps)
produced seven findings; all are closed, and the same pass landed the v0.8
community-extension surface. Each decision recorded, numbers load-disclosed in
the README/test docstrings.

1. **The pure-insert/delete/replace "unambiguous class" was falsifiable**
   (HIGH). difflib's find_longest_match anchors a ROTATED longer equal block
   on repeated-flank contexts and emits a NON-MINIMAL insert+delete split
   (`"qpqpq"` vs `"qpwqpq"`: difflib `[insert 3, equal, delete 2]` vs tors's
   minimal `[equal, insert, equal]`) — the generator's differing-flanks guard
   does not exclude the class, so the exact-parity tests were flaky-red on
   every CI leg (observed failing on 3.13.14/3.14.0 draws). DECISION: exact
   agreement is now pinned only where difflib's own answer carries the
   canonical single-op shape (the honest definition of "forced"); new
   tors-side canonical properties (tors emits exactly one insert/delete/
   replace op on every pure-class pair) hold on ~4.5M swept pairs and are
   pinned at full strength; the counterexample joined the boundary pins; the
   README/api.md claims rescoped to the forced-shape wording.
2. **test_parity's residual bound `< 200` was calibrated on one UCD**
   (HIGH). Measured per leg: 3.10.21 → 356, 3.11.16 → 238 (both red); the
   bound now scales with the UCD gap (`< 60 + 130 × (16 −
   unidata_version_major)`), every leg ≥ 1.26× headroom, the load-bearing
   zero-ASSIGNED-divergence assertion unchanged and still green everywhere.
   One honest discovery recorded in the test docstring: even the matched-UCD
   leg is not perfectly clean (3.14.0 residual 2, both on U+A7F1 — the
   crate's 16.0 snapshot maps it under NFKC where CPython 3.14's own tables
   do not; still confined to interpreter-unassigned codepoints).
3. **html_unescape's over-limit ValueError message was version-blind**
   (MED-HIGH). CPython's wording differs ("limit (4300)" on 3.10.7–3.11.x,
   "limit (4300 digits)" on 3.12+), and the limit EXISTS on 3.10.7+ (the
   CVE-2020-10735 backport — the earlier claim that 3.10 has no limit was
   wrong; only 3.10.0–3.10.6 lack it). DECISION: the error path REPLAYS the
   running interpreter's `int()` on the offending digit run and raises the
   very ValueError it returns — exact message on every interpreter, no
   version logic, honors `sys.set_int_max_str_digits()` mid-stream; the
   recorded shape is the fallback only. The error carries the digit run
   (one O(run) copy on the error path — CPython's own `html.unescape` pays
   the same `int()` on the same run). Verified green on 3.10.21/3.11.16/3.12.7.
4. **`diff_opcodes(deadline_ms=1e300)` panicked** (MED): a finite positive
   value passed the wrapper's validation and reached
   `Duration::from_secs_f64` (pyo3 PanicException). DECISION: the core
   saturates any `Duration` overflow to unbounded
   (`try_from_secs_f64().unwrap_or(Duration::MAX)`, plus
   `checked_add` for the similar-side Instant — `Instant + MAX` itself
   panics), so an enormous budget reads as "unbounded by heat death" and the
   core is panic-free for every f64; pinned crate-side and probed from
   Python (1e300 returns opcodes, no exception).
5. **The opcode tag strings were not actually interned** (MED): the docs
   claimed "difflib's own interned-tag shape" but `PyString::new` per call
   meant `op[0] is "equal"` was False where difflib's is True. DECISION:
   `PyString::intern` for the four tags in the shared marshalling helper
   (both diff spellings) — the `is`-check now holds, and the claim is true.
6. **LOW batch**: the stale `_tors.cpython-312-*.so` shadow deleted from
   the working tree (gitignored, never shipped — the wheel was inspected);
   the README's transitive-closure record refreshed to the current lock
   (105 dependency packages).

The **v0.8 community extension** (the user-hat pass: what is GIL-held or
missing in CPython that downstream text pipelines — tastack, cennan, warden,
and the community — actually reach for), engine choices re-validated against
